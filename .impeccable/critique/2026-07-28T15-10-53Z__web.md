## Design Specificity Verdict

**LLM assessment**: This is not generic-dashboard boilerplate. The domain vocabulary (typology T0–T5, €/m², freguesia, Portuguese keyword categories like "a aguardar licença"), the deliberate one-accent-color restraint, and the native-platform-first choices (Popover API, `<dialog>`, `:user-invalid`) all show real authorship for this specific operator and this specific domain. `globals.css` faithfully implements `DESIGN.md`'s palette and shadow vocabulary. But the system's central promise — "numbers are the hero, everything else recedes" — breaks down exactly where it matters most: on the real 731-lead dataset, title text (often a raw truncated description) visually outweighs the price/€/m²/discount stat block, and the discount signal that's the entire reason this product exists never fires once. The design system is well-authored; its application to messy real data is not yet finished.

## Overall Impression

The visual system itself is disciplined and well-executed — genuinely one of the stronger vanilla-CSS design-token implementations I've reviewed, and it holds up on clean/empty states. But it hasn't yet been pressure-tested against the real data it's meant to serve: 731 real leads expose that the flagship "hot lead" feature is completely dormant, the dashboard has no way to search or sort through them, titles regularly render as garbled truncated fragments, and a CSS specificity bug silently breaks every primary button's hover state app-wide. The single biggest opportunity: make the product's core promise (surfacing undervalued leads) actually visible against the real dataset — right now the tool that exists specifically to make undervalued properties surface on their own ends every visit exactly the way it started.

## What's Working

- **`PhotoCarousel`'s empty state** (`web/src/components/PhotoCarousel.tsx`): a calm inline-SVG placeholder with "No photo available" text, explicitly rejecting fabricated imagery per its own code comment — a disciplined, direct match to this project's "real data over fabricated polish" principle.
- **Native-platform-first interaction model**: Popover API for triage assignment, `<dialog>` for the add-search modal, `:user-invalid` for validation timing — all deliver the "calm, understated" brief with zero added JS libraries, and all were verified to behave correctly.
- **`:user-invalid` discipline**: every form field validation across Settings/Keywords/Saved-Search modal waits for real interaction before painting red — a small, easy-to-skip detail implemented consistently everywhere it applies.

## Priority Issues

**[P0] The flagship "hot lead" signal never fires on real data.**
**Why it matters**: All 731 migrated leads render `discountPct: null` ("—"); zero cards get the hot-lead treatment. The lead detail page confirms why for at least one area ("No baseline available for Campo de Ourique yet."). The product's entire stated purpose — undervalued properties surfacing on their own — doesn't happen anywhere in the real dataset, and there's no visual distinction between "not yet evaluated" and "evaluated, not a deal," so the operator can't tell whether the feature is dormant or just returning no hits.
**Fix**: Populate/backfill `AreaPriceBaseline` for the migrated areas (this is a known, already-documented gap — see HANDOFF.md's baselines-never-triggered item), and give "not yet evaluated" its own visible state distinct from "evaluated, —".
**Suggested command**: `/impeccable clarify` (empty/unknown-state copy) once baselines are backfilled, or treat as a data/backend task outside Impeccable's scope.

**[P1] No search, filter, or sort on a 731-card dashboard.**
**Why it matters**: Confirmed zero search/sort/filter controls exist; the only ordering is a hardcoded `lastSeenAt desc`. This is the highest-traffic screen in a tool whose entire premise is fast, repeated triage over hundreds of leads.
**Fix**: At minimum, a hot/status filter and a discount or €/m² sort; pagination or virtualization to bound render cost as the dataset grows past 731.
**Suggested command**: `/impeccable shape` (plan the filter/sort UX before building it).

**[P1] `.button--primary`'s hover state silently loses its gradient app-wide — confirmed live.**
**Why it matters**: `.button:hover { background: var(--color-border); }` (the base button rule) has higher CSS specificity than `.button--primary`'s own resting `background: var(--gradient-brand)`, and `.button--primary:hover` only overrides `box-shadow`, not `background`. On hover, every primary button (Save settings, Add new search, Save/Assign, etc.) drops to a pale near-white background with white text still on top — reading as disabled, not as a normal hover state. Verified directly: computed `backgroundImage` is `"none"` on hover vs. the correct gradient at rest.
**Fix**: Add an explicit `.button--primary:hover { background: var(--gradient-brand); }` (or a slightly deepened variant) alongside the existing shadow escalation, so specificity can't let the generic rule win.
**Suggested command**: `/impeccable polish`.

**[P1] Titles truncate mid-token into garbled strings across most of the real dataset.**
**Why it matters**: Sampled dashboard titles show the majority ending mid-number/mid-word (e.g. "...Campo de Ourique 239.00…", "...Arroios 249.000 € 260.000 € 4…"). This string is the single largest, boldest element on the card, the detail page's `<h1>`, and the browser tab title — directly inverting `DESIGN.md`'s own "Numeral Precedence Rule" that numbers must outrank labels/titles.
**Fix**: Truncate `displayTitle()` on a whitespace/token boundary instead of a raw character count, and strip trailing partial digits. Consider visually de-emphasizing a synthesized (non-authored) title relative to the stat block, since the function already knows which case it's in.
**Suggested command**: `/impeccable polish` or `/impeccable typeset`.

**[P2] Leaked raw scraper text and duplicated location line on the lead detail page.**
**Why it matters**: The location line renders `"Campo de Ourique (Campo de Ourique) — Campo de Ourique"` when area/municipality/raw-location-text coincide; the Description section verbatim includes scraped UI chrome — "Contactar Ligar Ver telefone Excluir Guardar" (Contact/Call/See-phone/Delete/Save button labels from the original listing page). This is the screen the operator reads most closely per lead, and it currently reads as broken, not just unpolished.
**Fix**: De-duplicate the location line when values collide; extend the chrome-stripping already applied to the photo-counter/map-disclaimer prefix in `lib/leads.ts` to the description body too.
**Suggested command**: `/impeccable harden` (real-data edge case cleanup) or `/impeccable polish`.

## Minor Observations

- **Contrast**: "Ink Faint" (stat labels PRICE/€/M²/DISCOUNT, portal name, sidebar footer) measures 3.45:1 against Paper — below WCAG AA's 4.5:1 for normal-size (0.75rem) text.
- **Mobile sidebar spec mismatch**: `DESIGN.md` states the sidebar becomes a horizontal top bar under 720px; the actual CSS only collapses the content grid — `.sidebar` keeps `flex-direction: column`, so a 390px viewport shows a full vertical nav filling the entire first screen before any page content.
- Triage's sidebar icon is a trash-can shape, semantically mismatched with its actual function (assign an area to a lead).
- `LeadCard`'s `<article aria-label={title}>` duplicates the same text a screen reader hits again moments later on the inner `<h3>`/`<Link>` — mild redundant double-announcement.
- Saved Searches and Alerts are both currently empty (0 rows) — worth confirming this is a fixture/pipeline-not-yet-run gap rather than a UI issue, since it means those two screens' real-world density couldn't be evaluated against live data.
- The "N" circle bottom-left that appears to overlap sidebar caption text on some pages is Next.js's own dev-mode toolbar, not app code — will not appear in production, no action needed.

## Questions to Consider
